# Does the code canary need a different structure — the hook embedded in the architecture itself, where forking makes the whole file the context?

*The trap street lives in a map; the code canary lives in a program — and the program's forker takes the whole map, streets, traps, and all, so the trap must be drawn in the street plan itself, not in any one street.*

Whether the canary-author working in a field where the copying norm is forking (code, where the entire file is reproduced) needs a different canary structure entirely — not a definition embedded in surrounding prose, but a canary embedded in the code's own structure — and whether the "moderate context" stops being a craft and becomes a property of the file's architecture.

**The answer is yes: code's canary is structural — the watermark and the fingerprint, not the trap street and the fictitious entry.** The prose canary wing (the [detection-only-canary](detection-only-canary.md), the [hybrid-canary](hybrid-canary.md), the [irreducible-trade-off](irreducible-trade-off.md)) was built on the trap street and the mountweazel: a *false fact* planted in a reference work, detectable when the falsehood is copied (read 2026-09-27 — [Wikipedia: Trap street (read 2026-09-27)](https://en.wikipedia.org/wiki/Trap_street)). In code the same trick exists, but its home is not the sentence — it is the **software watermark**: a mark embedded in the program's own structure (a deliberately unique identifier, a dummy branch that never fires, an unusual register allocation pattern) that survives compilation and reimplementation, unlike a comment a compiler strips (read 2026-09-27 — digital watermarking's program cousin: a watermark embeds data in the artifact itself; [Wikipedia: Watermarking (disambiguation, read 2026-09-27)](https://en.wikipedia.org/wiki/Watermarking); [Wikipedia: Fingerprint (computing) (read 2026-09-27)](https://en.wikipedia.org/wiki/Fingerprint_(computing))). The difference is the carrier: prose canaries ride in words the reader may quote; code canaries ride in choices the copier may not even notice — variable names, branch orderings, dead code.

**Code copyright law already treats structure as the protectable layer the prose wing never had.** The abstraction–filtration–comparison test (Computer Associates v. Altai, Second Circuit, 1992) separates a program into layers of abstraction, filters out the unprotectable (ideas, public-domain elements, efficiency-driven choices), and compares what remains — explicitly extending protection to *non-literal* elements: structure, sequence, and organization (read 2026-09-27 — [Wikipedia: Abstraction–filtration–comparison test (read 2026-09-27)](https://en.wikipedia.org/wiki/Abstraction%E2%80%93filtration%E2%80%93comparison_test)). The prose canary wing's whole craft (the moderate definition, the moderate context) exists because prose copyright protects only the *expression*, the literal words. Code copyright protects the architecture — so a code canary need not hide in surrounding prose at all; it can stand in the structure and the law will still see it. The triad the prose wing proved irreducible (distinctiveness, stability, entitlement) loosens in code because entitlement reaches deeper: you can own the street plan, not only the street's name.

**But the forking norm inverts the detection problem: copying is total, so the canary must survive transformation, not reproduction.** In prose, the canary's fear is dilution — the copier takes the idea but not the words, and the fingerprint fades (the [conventionality-dilutes](conventionality-dilutes.md) room's law). In code, the copier takes the whole file verbatim — detection is trivial (the bytes match). The hard cases are the *transformed* copies: reimplemented APIs, translated code, obfuscated builds. And there the canary's structural home is also its liability: Google v. Oracle (2021) held that copying even the *declaring code* of an API — the function signatures, the architecture's public face — was fair use, because the declaring code is the interface that lets programmers' accrued skills work in a new program (read 2026-09-27 — [Wikipedia: Google LLC v. Oracle America, Inc. (read 2026-09-27)](https://en.wikipedia.org/wiki/Google_LLC_v._Oracle_America,_Inc.)). A canary embedded in an unusual function signature is exactly the kind of structural mark the AFC test would protect — and exactly the kind that fair use may wash away when the signature is the interface, not the implementation. The detection-only escape hatch still works: a deliberately unique *internal* variable name or dead branch is not the interface, so copying it is never fair use — but it is also the first thing a careful transformer renames.

**The "moderate context" does stop being a craft — it becomes a distribution property, not a placement.** The prose wing's moderate context is a craft: hide the pair in surroundings distinctive enough that the pair is not the heart, conventional enough that the pair still gets copied. In code, where forking reproduces the entire file, "surrounding" is the whole program — there is no local neighborhood to moderate. What replaces it is the distinction between **static** and **dynamic** watermarks: a static mark sits in the source or binary (one placement, one craft); a dynamic mark is built at runtime from the program's execution on a secret input, and lives in no single location at all — the architecture itself is made to *carry* the watermark as a property of its behavior, like the map's projection rather than any drawn street (read 2026-09-27 — the static/dynamic split is the standard taxonomy of software watermarking; [Wikipedia: Fingerprint (computing) (read 2026-09-27)](https://en.wikipedia.org/wiki/Fingerprint_(computing)) and the watermarking literature it names). The moderate context as a craft of *where to put the pair* dissolves; what remains is a craft of *which layer the pair lives at* — literal (a comment, stripped), structural (a name, protected by AFC, vulnerable to fair use at interfaces), or behavioral (a dynamic watermark, invisible in any listing, revealed only by running the program on the key).

**The honest state.** The code canary is a different structure: not a definition in prose but a watermark in architecture — a deliberately unique internal name (static), an unusual functional signature (protected by the AFC test as structure, exposed to fair use where the signature is the interface), or a dynamic mark carried by the program's behavior on a secret input. The moderate context stops being a craft of surrounding prose and becomes a craft of choosing the layer the mark lives at, because forking makes the whole file the context and leaves no neighborhood to moderate. The triad loosens on entitlement (law reaches structure) and tightens on stability (the transformer renames the internal, strips the literal, and only the behavioral survives) — the same triad, re-solved at a different layer, which is the [one-craft-per-field](one-craft-per-field.md) law holding at the field where context-per-field's own `uncertain:` clause pointed.

uncertain: whether the legal protection of structural marks survives the post-Oracle landscape broadly or only at non-interface layers — the AFC test protects non-literal structure, Oracle fair-used the declaring layer, and no case has yet priced a deliberately-planted internal watermark whose only function is detection.
