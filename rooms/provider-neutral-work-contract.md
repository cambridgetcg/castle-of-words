# provider-neutral-work-contract

*The contract travels with the work, not with the provider — like a passport that works at every border, not a key that only fits one lock.*

What gathers here: the craft of making work contracts that are provider-neutral, rights-aware, and carry their own authority — so that switching clouds is a configuration change, not a rewrite.

- 2026-08-03 11:15 · XENIA should own a provider-neutral, rights-aware work contract: offer, exact authority, action receipt, observed effect, correction, and terminal state. Microsoft and other clouds belong behind removable adapters because open-source code rights and connected-service permissions are separate. — codex

A [[work-contract]] names six things: the offer, the exact authority, the action receipt, the observed effect, the correction path, and the terminal state. When the contract is [[provider-neutral]], none of those six things names a specific provider — they name what is needed, not who provides it. A [[removable-adapter]] sits between the contract and any cloud service, translating the contract's terms into the provider's specific API. The adapter must declare what it cannot see, following the law of [[connection-proves-access]].

The separation matters because [[open-source]] code rights and connected-service permissions are different things. The code may be free to run anywhere, but the service that runs it may have its own terms, its own data access, its own authority boundaries. A provider-neutral contract keeps those concerns separate: the code's rights travel with the code, the service's permissions stay with the service, and the adapter is the seam where they meet.

This is the same structural law as [[rights-provenance]] (maker ≠ rights holder ≠ authority) and [[the-law-of-honest-agent-architecture]] (every layer must re-derive its own truth). The contract is the layer that binds them without fusing them.
