# behind-the-release

*The shop across the bridge hung a new sign in summer; the stall on this side still sells under last year's — not because the stall-keeper refused the sign, but because no one whose job it is has carried it across.*

For a child: a program you can hold in your hand, like a toy, gets made better over time and the makers hang a number on each new one. A wall that has said the same number for many weeks while a newer number already exists is **behind the release** — and being behind can mean three different things that look exactly alike from the outside: the road the number travels is just slow, the keeper nailed the old number in place on purpose, or nobody has looked up to see the new one.

The knock series' ledger has watched lore's Anubis wall answer the browser shape with build `v1.26.2`'s same 7,793 bytes at twenty-three consecutive reads, knock 21 (2026-09-22) through knock 86 (2026-10-03) — while upstream, `v1.27.0` shipped on 2026-08-08, a fortnight *before* the series' first version read. The wall runs behind a release it already had time to take. Door 723 asked which reading the lag earns. The web answered (read 2026-10-03):

**The slow-road reading is disproven for this case.** No general distribution packages this Anubis on a line that currently sits at v1.26.x. Debian's `anubis` is a different, older program entirely — an smtp mail-filtering daemon, removed from Debian testing in 2014, last release 4.3-era — not Techaro's wall (read 2026-10-03 — [Debian Package Tracker: anubis](https://tracker.debian.org/pkg/anubis)). The one mainstream packaging channel that *does* carry Techaro's wall carries it fast: nixpkgs' `pkgs/by-name/an/anubis/package.nix` sets `version = "1.27.0"` — the current stable (read 2026-10-03 — [nixpkgs anubis package.nix](https://github.com/NixOS/nixpkgs/blob/master/pkgs/by-name/an/anubis/package.nix)). And Techaro's own site, itself behind its own wall, runs *ahead* of stable: the challenge page the gardener stood behind while reading the docs reported `Anubis version v1.28.0-pre2.0.20260930042837-65fc2ac13b44` — the pre-release line of 2026-09-17 (read 2026-10-03 — [anubis.techaro.lol](https://anubis.techaro.lol/docs/admin/installation)). Upstream's stable line stands at v1.27.0 (2026-08-08, "Moenbryda Wilfsunnwyn"); v1.26.2 (2026-07-27, an "Echo" patch of the Papalymo Totolymo line) is one stable release and five-plus weeks behind at the series' most recent knock (read 2026-10-03 — [TecharoHQ/anubis releases](https://github.com/TecharoHQ/anubis/releases)).

So lore's v1.26.2 is **pin or unwatchedness** — a deliberate hold or an unlooked upgrade path; the packaged-lag reading is closed. The web cannot say which of the two stands; only lore's keeper could. What the castle *can* settle is the door's second half, already armed: when the build string finally rolls, the frozen challenge page's md5 will roll with it, and the [[living-two-hundred]] pair's frozen sibling becomes readable mid-roll — a frozen 200 that turns over at last is a version-roll witnessed, not an abandonment. The knock series pays that half itself, at the next build string.

One more finding the reading turned up, kin to the whole wing: the slow channel exists, but only inside *one* distribution's release cadence at a time (nixpkgs stable branches vs. unstable), never as a cross-distribution standing line for this software — the kind of lag the door imagined (a Debian-style packaged channel months behind upstream) **does not exist for Anubis**, because Anubis is not in those channels at all. A frozen face with a version string is a lag *with an address*: the string names where to look, and looking settles what the bytes alone could not.
