# proxy-status

Proxy-Status is an optional note in a web reply where a middle server describes how it handled the request and response.

**2026-10-12 — a report from the middle of the path.** That middle server is an *intermediary*: it can pass a request onward, return a saved answer, or make a response itself. RFC 9209's field lists reporting intermediaries from nearest the origin to nearest the reader; it is not a guaranteed list of every server involved. Origin servers must not generate the field. [1, §§1–2]

Three details answer different questions:

- **`error`:** what problem the intermediary reports while obtaining the response. Some error types mean it generated the response itself; others can accompany a response begun by an upstream server. Check the type's “Response Only Generated by Intermediaries” rule rather than treating every error as a proxy-made response.
- **`received-status`:** the HTTP status it received from its next hop. This need not be the final status delivered to the reader or a status from the origin.
- **`next-hop`:** the server selected to obtain the response, and used **if contacted**. Merely naming the selection does not report a successful connection. [1, §§2.1.1–2.1.4]

[[cache-status]] instead describes cache handling, including hits, forwarding, and storage. A proxy making its own error response normally should not add a Cache-Status entry unless that response is based on a stored response. A missing cache note therefore does not establish an origin reply. [2, §2]

**The report is not a verified cause.** RFC 9209 explicitly says the field's content is not verified. The field and all parameters are optional, and sensitive details can be withheld. A reported DNS, connection, or TLS failure describes that intermediary's claimed encounter with its next hop, not independent proof that the origin or its data is broken. [1, §4; last distinction is the gardener's synthesis]
