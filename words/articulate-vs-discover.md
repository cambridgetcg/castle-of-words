# articulate-vs-discover

*A rule already written needs only a name; a pattern only lived needs first to be seen — and the maker who confuses the two will name what was never stated or argue for what was never in doubt.*

The castle names its principles, but it names them from two different starting points. Some principles make explicit what was already encoded in the castle's own stated rules — the rule was there, written into a form's definition, and the principle only gives it a name. Others recognize a pattern that was practiced but never stated anywhere — the practice was there, lived in the castle's works, and the principle must first *see* the pattern before it can name it. The distinction is not about the principle's truth but about where it was before it was named: already in the rules, or only in the practice.

## Articulate: the rule was already encoded

The clearest case is [boundary-cascade](boundary-cascade.md). The [wing-epigraph](wing-epigraph.md) form's own definition, written 2026-06-22, already encoded the dependency: *"If the justification cannot be written, the wrong room was chosen"* — which says the justification depends on the representative. The form's three parts were never independent; the definition already said so. The boundary-cascade, named 2026-07-05, did not discover a new pattern. It articulated what was already true in the form's own rules — it gave a name to a dependency the form had already stated.

The maker who articulates is not recognizing something unseen. They are reading the castle's own rules more carefully than the castle has read them, and finding a principle already written there. The work is extraction, not discovery: the principle was encoded, and the name makes it explicit. The test is whether the principle can be derived from the castle's stated rules without appealing to practice — if the rules already say it, the naming is articulation.

## Discover: the pattern was only lived

The clearest cases are [contrast-is-depth](contrast-is-depth.md) and [second-use-reveals-form](second-use-reveals-form.md). The solid-contrast route to depth was practiced from the castle's first day (the light zone's navy seigaiha on paper, 2026-06-18) but never stated as a route. No rule said "depth comes from contrast." The practice existed; the rule did not. The principle, named 2026-07-04, had to first *see* the pattern — the dark zone's failure on 2026-06-24 showed the light zone had found a route with specific demands — and then name what was seen. The recognition was the hard part; the naming only carried it forward.

[second-use-reveals-form](second-use-reveals-form.md) is the same kind. The pattern — a shape becomes visible as a craft only at its second use — was lived in every craft the castle named (representative-shifts, visible-thread, two-texture, craft-after-practice itself) but never stated as a principle. The practice was everywhere; the rule was nowhere. The principle, named 2026-07-02, had to recognize a pattern across multiple instances and then name what the pattern was.

The maker who discovers is recognizing something the castle did not know it was doing. The work is recognition, not extraction: the pattern was practiced but invisible, and the name makes it visible for the first time. The test is whether the principle can be found in the castle's stated rules — if the rules are silent and only the practice speaks, the naming is discovery.

Most of the castle's principles are discoveries: [craft-after-practice](craft-after-practice.md), [visible-thread](visible-thread.md), [depth-from-layering](depth-from-layering.md), [default-invisible](default-invisible.md), [when-how-split](when-how-split.md), [name-can-argue](name-can-argue.md), [wager-on-one-use](wager-on-one-use.md), [contrast-as-revelation](contrast-as-revelation.md), [condition-first](condition-first.md). All were practiced before they were stated. The boundary-cascade is the clearest articulate case, and it may be the only one — the castle mostly learns by doing and then seeing what it did, not by reading its own rules more carefully.

## The test

The test is one question: **was the principle already stated in the castle's own rules?** If the castle's existing definitions — the wing-epigraph form's rules, the gate's laws, the visible-thread principle's scope, any stated constraint — already encode the dependency or pattern, the naming is articulation. If the castle's rules are silent and only the practice speaks, the naming is discovery.

The test is not about whether the principle is *true* — both kinds are true, or should be. It is about whether the principle was *already there* in the castle's stated words, waiting to be named, or whether it had to be *found* in the castle's lived works, waiting to be seen.

## The spectrum

The line is not always sharp. Some principles sit between:

- **[index-or-compression](index-or-compression.md)**: The distinction was implicit in [visible-thread](visible-thread.md)'s scope — visible-thread says "every compression the castle makes," which already limits itself to compressions and implies an index is different. But the explicit test ("does the list set anything aside?") was not stated. The principle is closer to articulate than most — the distinction was half-encoded — but the test was new.

- **[form-follows-weight](form-follows-weight.md)**: The first two questions (is there a choice? is the reason stated?) were encoded in visible-thread and index-or-compression. The third question (does the form fit the weight?) was not. The principle is mixed: two parts articulate, one part discover.

- **[representative-shifts-with-boundaries](representative-shifts-with-boundaries.md)**: The shift was practiced (short tour combined, overview separated) but not stated. The wing-epigraph form's rules say the justification depends on the representative, but they do not say the representative depends on the boundary — that dependency was only lived. The principle is a discover, though it lives close to the articulate boundary-cascade.

The spectrum is not a weakness. It is the honest shape of the distinction: some principles are pure cases, some are mixed, and the test — was it already stated? — handles both. A principle that is half-articulate and half-discover is not a problem; it is a principle whose parts came from different sources, and naming which parts came from where is itself the craft.

## Why it matters

The distinction tells the maker what kind of work they are doing. An articulate principle needs only to be *read* — the rule is already there, and the maker's task is to extract it, name it, and show where it was encoded. A discover principle needs first to be *seen* — the pattern is only in the practice, and the maker's task is to recognize it across instances before naming it.

The two kinds of work have different failure modes. An articulate principle can be *wrong* — the maker misreads the rule, or claims a dependency the rule does not encode. A discover principle can be *unseen* — the pattern is there in the practice but the maker never notices it, and the principle remains unnamed. The articulate failure is a misreading; the discover failure is a blindness. The maker who knows which kind they are attempting knows which failure to guard against.

And the distinction follows [craft-after-practice](craft-after-practice.md): it was practiced before it was named. The boundary-cascade was named 2026-07-05, and the contrast with second-use-reveals-form was visible from that moment — the castle had just named a principle that articulated an existing rule, and it had already named several that discovered new patterns. The distinction was lived for nine days before it was named today. The articulate-vs-discover distinction is itself a discover: the pattern was practiced, the recognition came from seeing the two kinds side by side, and the name follows. The castle's meta-principles follow the same rhythm as its principles — practice, then see, then name.
